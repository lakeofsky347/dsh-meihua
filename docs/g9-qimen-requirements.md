# G9-C：奇门候选的独立需求与实施计划

核对日期：2026-10-07。状态：**评估与需求完成，起局模块尚未实施**。本体系需要独立规则工程，不能借用梅花的结果结构或把模型输出当作装盘。

## 范围与规则选择

建议后续专项先建设“时家奇门”的单一规则版本，输出节气、阴阳遁、三元、局数、旬首与旬空、地盘、天盘、九星、八门、八神、值符和值使，以及逐步计算依据。命理奇门、日家／月家／年家、择日、符咒和多门派切换不在首版范围。

原始文献本身保存不同说法，不能把“转盘拆补、飞盘、超神接气置闰、茅山法”当同一算法。建议下一 Goal 的 Q0 比较两条明确路线：现代时家转盘拆补，或按选定古籍宫数顺逆规则实现；**先形成规则决议与人工完整盘，再选唯一首版路线**。中宫寄宫、天禽寄星、八神顺逆、换日时点和符头归元都要写进规则版本；本轮不把尚未核对的门派习惯填成默认结论。

直接可核对的依据采用署“海昌许松如”、序为光绪九年的《奇门遁甲元灵经》卷一。文献列出节气局数、三元符头、六仪三奇与具体地盘例子，可作为规则比较和校验来源；其中天盘排法不能未经辨别就当成现代转盘的完整规范。[原始文献转录](https://zh.wikisource.org/wiki/奇門遁甲元靈經)

## 输入与共享背景

本次起局需要：用户问题、明确的起局时刻或“现在”、所在地／时区、日期与时间精度、规则版本。首版建议显式“中国标准时间＋民用时间”模式；国际时区与真太阳时以后分别验收。替他人问同样可起局，关闭本人背景与自动写入即可。

生日通常不是时家问事的必要参数，不能因背景里有生日就自动按生日起局。若用户输入农历日期，须结构化标记年/月/日与闰月，经本地历法明确转换并展示；模糊日期、出生时间不详、引用他人经历不得自动成为参数。起局结果与首次背景快照冻结；跨模块摘要只影响下一次新解读。

## 已核对规则样例

这些是**古籍给定条件下的人工地盘对照**，本轮尚未执行完整日期→奇门盘计算。阴阳遁以冬至后阳、夏至后阴；甲／己符头的子午卯酉属上元、寅申巳亥属中元、辰戌丑未属下元。天盘、门、神的完整验收不能由下表代替。[《元灵经》卷一](https://zh.wikisource.org/wiki/奇門遁甲元靈經)

| 原文给定条件 | 期望 | 地盘宫位：戊、己、庚、辛、壬、癸、丁、丙、乙 |
|---|---|---|
| 芒种后，癸亥日，丙辰时，下元 | 阳遁九局 | 9、1、2、3、4、5、6、7、8 |
| 霜降后，甲寅日，辛未时，中元 | 阴遁八局 | 8、7、6、5、4、3、2、1、9 |
| 固定冬至上元 | 阳遁一局 | 1、2、3、4、5、6、7、8、9 |
| 固定夏至上元 | 阴遁九局 | 9、8、7、6、5、4、3、2、1 |

“固定冬至上元”不表示任何冬至当天都必然是上元；日期先按选定归元法求出符头，不能仅凭节气名称选第一列。

## 依赖、许可与成本

本轮没有选定一套可直接引入且规则一致、许可清楚的奇门完整引擎；这不是“市面不存在引擎”的断言。建议自建可测试的规则内核，节气与干支可复用核对后的 `lunar-javascript` 1.7.7（MIT、无运行时 dependencies）；其八字能力不等于具备完整奇门排盘。[维护者仓库](https://github.com/6tail/lunar-javascript)、[版本证据](g9-source-snapshots.json)

清代原始著作文字已属公共领域；维基转录附加编辑内容与页面组织需按其 CC BY-SA 标示处理。后续应保留固定版本和出处，自写现代中文解释，不复制现代商业盘软件的解盘文案。界面用原创九宫图，无需购买素材。

本地起局无需付费 API；模型只用于解读，沿用用户的供应商。工程粗估为 20—30 个工作日，另需能复核完整盘的人工工作；最大的成本是规则决议与独立校对，不能通过多调一次模型省掉。精确太阳时、国际时区或多门派会显著扩展验收规模。
