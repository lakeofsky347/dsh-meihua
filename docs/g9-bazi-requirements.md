# G9-A：八字候选的独立需求与实施计划

核对日期：2026-10-07。状态：**评估与需求完成，八字排盘模块尚未实施**。本文件给出可进入后续专项 Goal 的范围；库的上游八字测试期望已经查阅，本轮 G9 评估没有新增安装或执行八字适配器，也没有调用真实模型。

## 产品范围与输入

首版建议交付四柱、藏干、五行、十神、旬空和计算依据。展示“输入 → 历法与换日规则 → 四柱 → 通俗解释”；追问继续使用首次冻结的命盘和背景。大运、流年、合婚、喜用神评分和出生时间反推不进入第一阶段，避免把不同规则混成一个确定结论。

需要一个**本次排盘专用的结构化输入**，这不等于修改 0.4 的共享背景文档方案。字段包括：公历或农历、年/月/日、农历闰月标志、出生时间精度（准确到分钟／只知时辰／不详）、时分、出生地、明确选定的时区、历史夏令时歧义选项，以及排盘规则版本。日期范围首版建议限制为 1900—2100 年，超范围拒绝排盘；扩大范围另做历法核对。

背景文档里的“1990 年农历六月出生”“大概晚上”等原文可以在旁边供用户参考，**不得由模型自动转成公历、闰月、地点、时区或具体时刻**。仅用户明确确认的结构化字段可参与计算。时间不详时显示三柱及“时柱未知”；只知时辰时不输出虚假的精确分钟。地点未知不能默认当作北京；首版可先提供显式选择的“中国标准时间模式”，国际出生输入在历史时区验证完成后再开放。

输入默认只保存在当前解密会话；若未来提供“保存此次出生输入”，须沿用 MemoryService 的加密记录、清空与 epoch 机制，不能增加明文个人资料文件。日主、十神等排盘结果不能自动写成本人事实。替他人排盘沿用关闭本人背景与自动写入的模式。

## 拟固定的历法规则

采用 `lunar-javascript` 作为历法候选，由独立适配器返回稳定的内部结果，界面不直接调用库。年柱按立春交接时刻、月柱按节交接时刻确定；农历新年不是默认年柱边界。晚子时必须作为可见规则选项：首版建议默认上游 EightChar 的 sect=2（日柱仍算当天），另提供 sect=1（日柱算次日）；两种时柱规则均保持上游规定，不能只改日柱后自造时柱。[官方八字文档](https://6tail.cn/calendar/lunar.bazi.html)、[上游测试](https://github.com/6tail/lunar-javascript/blob/master/__tests__/EightChar.test.js)

默认按用户确认的民用时间排盘。真太阳时暂不提供；后续加入时必须分别记录经度修正、均时差、民用时间、修正后时间和跨日结果，不得悄悄更改原始生日。时区适配不能把 UTC 年月日直接传给以本地日期为输入的历法库。国际时区需使用历史规则而非当下 UTC 偏移；IANA 当前发布为 2026e，实际宿主携带的 tzdb 版本须在实施时检测并写入结果。[IANA 时区数据库](https://www.iana.org/time-zones)

输出冻结 `ruleVersion`、`calendarLibraryVersion`、`timeZoneDataVersion`、原始输入、规范化输入、四柱、时柱可用性、换日选项、计算依据和背景快照版本。用户修改任一排盘输入即新建一次命盘，不重写正在追问的旧结果。

## 有来源的规则样例

以下期望直接来自上游 MIT 测试；状态为 **UPSTREAM_FIXTURE_NOT_RUN**，不能写成项目排盘测试通过。实施时要先运行适配器，再用另一套人工例盘核对，避免只测试包装层。

| 输入 | 规则 | 期望年／月／日／时柱 | 验证重点 |
|---|---|---|---|
| 公历 2005-12-23 08:37 | 上游默认 | 乙酉／戊子／辛巳／壬辰 | 基本四柱与分钟输入 |
| 公历 1988-02-15 23:30 | sect=2 | 戊辰／甲寅／庚子／戊子 | 晚子时仍为当天日柱 |
| 同一输入 | sect=1 | 戊辰／甲寅／辛丑／戊子 | 日柱换日，时柱保持上游规则 |
| 公历 1988-02-15 22:30 | 上游默认 | 戊辰／甲寅／庚子／丁亥 | 亥时与子时边界 |
| 农历 2019 年十二月十二 11:22 | 明确非闰月 | 己亥／丁丑／戊申／戊午 | 显式农历输入 |

同一上游样例 2005-12-23 的年、月、日、时藏干为“辛／癸／丙庚戊／戊乙癸”。这些样例不能替代立春和节交接前后一分钟、闰月、时间不详、历史夏令时重叠与不存在时刻的专项样例。[上游测试固定证据副本](g9-source-snapshots.json)

## 依赖、许可与成本

核对到 npm 当前 `lunar-javascript` **1.7.7**，MIT，包声明没有运行时 dependencies；测试工具 Jest 属于上游 devDependencies。本仓库六爻模块已保存同一版本的 vendor 源码及完整性摘要，仅用于节气与日干支历法适配；这不等于已实现八字排盘。本轮 G9 没有新增依赖安装或八字适配器执行。后续八字实施须明确复用或单独固定的依赖版本、完整性摘要和 MIT 声明，并完成八字规则验收。[现有六爻 vendor 来源记录](../src/liuyao/vendor/provenance.json)、[维护者仓库](https://github.com/6tail/lunar-javascript)、[npm 元数据](https://registry.npmjs.org/lunar-javascript/latest)

本地排盘无需模型、无需付费历法 API，库许可费用为零；AI 解读仍使用用户所选供应商，成本随其模型计价，本轮未测真实质量或费用。研发工作量粗估为 8—12 个开发工作日，另加人工例盘复核；这是工程预算而非报价。国际历史时区和真太阳时会扩大范围，应独立估时。
